# Сессия: `ContactPhoneExtractor` (релиз v1.1.7 перевыпускается, тег пересоздаётся)

## Проблема

Во **входящем** `ContactAttachmentPayload` поля `vcf_phone` нет (только `vcf_info`, `max_info`, `hash`), оно объявлено
лишь в исходящем payload, который бот кладёт сам. `Dto::$vcfPhone` на входе всегда `null`, и потребителям приходилось
писать разбор vCard самостоятельно. Реализация плана `.agents/plans/2026-09-30-contact-phone-extraction.md`.

## Решение

- `src/Security/ContactPhoneExtractor.php`: `final class` со статическим `fromVcf(string $vcfInfo): ?string`. Порядок:
  разделение по регулярке, покрывающей реальные `CRLF`/`CR`/`LF` и литералы `\r\n`/`\n`/`\r`; разворачивание свёрнутых
  строк vCard (строка с ведущим пробелом/табуляцией продолжает предыдущую); поиск по
  `/^TEL(?:;[^:]*)?:(.*)$/i`; обрезка пробелов; пустое значение `TEL` пропускается. Без состояния, HTTP, исключений и
  логирования.
- DTO и `ContactVerifier` не менялись: MINOR-релиз, только добавление публичного метода в новый класс.
- Шаблон `TEL` допускает префикс группы (`item1.TEL`, RFC 6350); `X-TEL` и `item1.X-TEL` под него не подходят, ложных
  срабатываний на кастомных свойствах нет.
- `docs/api-reference.md`: раздел 7 (контакт, попутно исправлена устаревшая формулировка про нормализацию CRLF — hash
  считается по сырым байтам с v1.1.3) и новая строка расхождения в разделе 9; `README.md` (возможности, безопасность с
  примером, таблица примеров, история v1.1.7); `AGENTS.md` (слой Security, контракт класса, gotcha 15, формулировка про
  `ContactVerifier`); `examples/verify-contact.php` выводит номер после успешной проверки;
  `.agents/release/RELEASE_NOTES_v1.1.7.md`.
- Рекомендуемый порядок в потребителе — `$contact->vcfPhone ?? fromVcf($contact->vcfInfo)` — перенесён в пример, README,
  раздел 7 `docs/api-reference.md`, gotcha 15 и release notes. Взят из интеграционного проекта i2tech, где так уже
  сделано в `RequestFlowService::applyContact()`: так код переживёт появление `vcf_phone` во входящем payload.
- Сверка с интеграционным проектом: их `RequestFlowService::telFromVcf()` проверена на 14 входах против нового класса.
  Совпадение на типичном профиле и на литеральных `\r\n`; новый класс полнее на свёрнутых строках (у них обрезанный
  номер), на строчном `tel:` (у них null), на префиксе группы и на CR-only переводах. Случаев, где их реализация лучше,
  нет. Их разбор стоит заменить на вызов пакета после выхода v1.1.7 — это правка чужого проекта, по запросу владельца.
- Отдельно исследовано получение телефона из мини-приложения через мост `window.WebApp.requestContact()`
  (`https://dev.max.ru/docs/webapps/bridge`): подпись к номеру проверяется на сервере, и пакет такого сценария не
  покрывает — ни `WebAppDataValidator` (только `initData`), ни `ContactVerifier` (только кнопка `request_contact`).
  Порядок аргументов HMAC в документации неоднозначен, без реального захвата схему не выбрать. Отдельный план на будущий
  релиз: `.agents/plans/2026-09-30-webapp-bridge-phone-verification.md` (v1.1.8).

## Нюансы

- Валидации и нормализации номера нет намеренно: значение `TEL` может быть любым текстом.
- Свёртка: снимается вся полоса ведущих пробелов, а не ровно один WSP, как в RFC 5545 §3.2. Отклонение задокументировано
  в docblock и закреплено тестом; для номера разницы в реальных vCard нет.
- Лог интеграционного проекта от 2026-09-17 (поле `vcf_escaped`) использован как реальный образец: после одного
  раскодирования JSON это `vcf_info` целиком — 110 байт, реальные CRLF, UTF-8 в `FN`, `TEL;TYPE=cell:79250000000`
  без `+`, `TEL` раньше `FN`, завершающий CRLF после `END:VCARD`. Парсер на нём отрабатывает, и по этому образцу
  синтетическая фикстура заменена на обезличенную копию реальной. Побочная правка: в README и документации пример
  значения исправлен с `+79250557481` на номер без `+` — в проде плюса нет.
- Решение по формату номера (потребитель, 2026-09-30): канон — значение, которое прислал MAX, ядро его не нормализует.
  Подтверждён единственный захват, и он российский, поэтому вопрос формы для других стран открыт; универсальную форму
  можно получить только с выборками из нескольких стран. Требование к потребителю уже сейчас: одно правило формы на все
  точки ввода, включая формы, иначе `+7...` из формы и `7...` из контакта дадут две записи об одном человеке. Разбор
  международных номеров — отдельная задача (giggsey/libphonenumber), не регулярное выражение здесь.
- Ограничение размера входа не добавлено: измерено, что 1 МБ из 512 тыс. коротких строк дают 780 мс и ~43 МБ, реальный
  vCard — микросекунды. Лимит тела вебхука — задача уровня `WebhookHandler::decode()`, а не чистого парсера.
- Сверка с интеграционным проектом: их `RequestFlowService::telFromVcf()` проверена на 14 входах против нового класса.
- Ограничение шаблона: двоеточие внутри кавычек в параметре обрывает параметры, в значение попадает хвост параметра;
  поведение зафиксировано тестом, чтобы изменение было осознанным.
- Фикстура vCard синтетическая: персональные данные в репозиторий не кладутся.
- Номер и `vcf_info` — персональные данные (A09): класс не логирует вовсе.
