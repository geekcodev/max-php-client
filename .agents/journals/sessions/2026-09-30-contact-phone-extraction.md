# Сессия: извлечение телефона из vCard контакта (request_contact)

## Проблема

Ядро подтверждает подлинность контакта, но номер телефона не отдаёт. У потребителя есть только `vcf_info`
(непрозрачная строка) и подпись, которую он проверил. Чтобы получить номер, каждый потребитель пишет разбор vCard сам.
Интеграционный проект i2tech так и делает: `RequestFlowService::telFromVcf()`.

## Исследование

- Во **входящем** `ContactAttachmentPayload` поля `vcf_phone` нет. `max-openapi/MAX_API_REFERENCE.md:2200-2206`
  даёт для входящего payload только `vcf_info`, `max_info` (объект `User`) и `hash`.
- `vcf_phone` есть только в **исходящем** `ContactAttachmentRequestPayload` (`:2258-2265`) — это то, что бот сам кладёт
  в своё вложение, а не то, что присылает MAX.
- Следствие: `Dto/ContactAttachmentPayload::$vcfPhone` на входе всегда `null`. Поле есть, заполняться ему нечем.
  Потребитель, доверившийся ему, получит `null` и потеряет номер.
- `src/Security/ContactVerifier.php` закрывает только подпись: HMAC-SHA256 токена над `vcf_info`, восстановление
  реальных CRLF из литеральных `\r\n`, приём хэша в hex и base64 (обычный и URL-safe, с паддингом и без), сравнение
  через `hash_equals`. Разбора полей vCard в ядре нет.
- Разбор в i2tech — `app/app/Services/RequestFlowService.php:1102-1113`, регулярное выражение с
  `(?:^|\r?\n)TEL(?:;[^:\r\n]*)*[:]`. Это единственный работающий путь получения номера сегодня.
- DTO в ядре чистые: только конструктор, `fromArray()`, `toArray()` (`Dto/MessageBody.php:18,42`). Хелперы в DTO не
  добавляем — это расходится с направлением плана v2.0.0.
- Стиль утилит: `src/Internal/Json.php` — `final class` со статическими методами. Новый класс соответствует.
- `docs/api-reference.md`, раздел 9 — таблица расхождений «спека vs реальный API» не содержит случая про отсутствие
  `vcf_phone` во входящем payload. Его нужно внести.
- Тест-стиль: `tests/ContactVerifierTest.php` — атрибут `#[Test]`, инлайн-строки vCard, включая профильный vCard с
  реальными CRLF и концевым переводом строки.
- `examples/verify-contact.php` показывает только проверку подписи.

## Решение

План `.agents/plans/2026-09-30-contact-phone-extraction.md`.

Новый `GeekCo\MaxPhpClient\Security\ContactPhoneExtractor` со статическим методом
`fromVcf(string $vcfInfo): ?string`. Порядок разбора: разделение регулярным выражением, покрывающим реальные
`CRLF`/`CR`/`LF` и их JSON-экранированные литералы; разворачивание свёрнутых строк vCard; поиск первой непустой строки
по шаблону `/^TEL(?:;[^:]*)?:(.*)$/i`; обрезка пробелов. Чистая функция, без HTTP, состояния, исключений и логирования.
`ContactVerifier` и DTO не меняются.

## Нюансы

- Свёрнутые строки обязательны: без их разворачивания длинный номер рвётся переносом, который в vCard допустим. Порядок
  «разделить, затем развернуть, затем искать» не переставлять.
- Литеральные `\r\n` встречаются из-за двойного экранирования в JSON-транспорте. `ContactVerifier` умеет оба варианта
  при хэшировании, разбор должен вести себя так же — иначе подпись пройдёт, а номер не извлечётся.
- Жадный `.*` в шаблоне сломает `TEL;TYPE=CELL`: параметры пропускаются классом `[^:]*`.
- Номер и `vcf_info` — персональные данные. Класс не логирует вовсе и не бросает исключений на битых данных; вызывающий
  код логирует только факт действия, но не значение.
- Валидации и нормализации номера намеренно нет: значение `TEL` может быть любым текстом, и ядро не должно отбрасывать
  валидные для бизнеса значения. Нормализация — ответственность потребителя.
