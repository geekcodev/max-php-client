# v1.1.1 — ContactVerifier: нормализация CRLF перед проверкой хеша (09.09.2026)

## Исправления

### Контакт из кнопки `request_contact` не проходил проверку подлинности

- `ContactVerifier::verify()` нормализовал только **литеральные** последовательности `\r\n` и `\n`
  (`str_replace(['\r\n', '\n'], "\n", $vcfInfo)` — в одинарных кавычках PHP это текстовая подстрока из символов `\`,
  `r`, `\`, `n`, а не байты CRLF/LF).
- В реальном вебхуке MAX `vcf_info` приходит как JSON-строка; после `json_decode` PHP-строка содержит **реальные байты**
  CRLF (0x0D 0x0A). Литеральная замена их не находила, `$normalized` оставался с переносами CRLF, и HMAC-хеш не совпадал
  с хешем, посчитанным по нормализованному (LF) контакту. Бот отклонял настоящий контакт пользователя («Не удалось
  проверить контакт»).
- Теперь `verify()` нормализует **обе формы** в порядке: сначала литеральные `\r\n`/`\n` (текстовые последовательности),
  затем реальные CRLF/CR-байты → LF (`src/Security/ContactVerifier.php`).

### Затронутые сценарии

- `ContactVerifier::verify($vcfInfo, $hash)` — принимает контакт и с реальными CRLF, и с литеральными `\r\n`/`\n`, и со
  смешанными переносами.
- Никаких изменений сигнатур и DTO — обратная совместимость полная.

## Обратная совместимость

- Не breaking: изменена только внутренняя нормализация строки перед хешированием.
- Все сценарии, ранее работавшие (литеральные `\r\n`/`\n`), продолжают работать.

## Качество

- PHP 8.4, PSR-12 (php-cs-fixer) — 0 замечаний; PHPStan level max — 0 ошибок.
- PHPUnit зелёные (227 тестов, 558 assertions).
- Тесты: `it_verifies_contact_hash_with_real_crlf_bytes` (реальные CRLF),

  `it_verifies_contact_hash` (литеральные `\r\n`) и `it_rejects_a_wrong_hash`.
