## Новое: извлечение номера телефона из контакта

`GeekCo\MaxPhpClient\Security\ContactPhoneExtractor::fromVcf(string $vcfInfo): ?string` — значение первого непустого
свойства `TEL` из `vcf_info` контакта по кнопке `request_contact` либо `null`.

```php
use GeekCo\MaxPhpClient\Security\ContactPhoneExtractor;
use GeekCo\MaxPhpClient\Security\ContactVerifier;

$verifier = new ContactVerifier(accessToken: $token);

if ($verifier->verify((string) $payload->vcfInfo, $payload->hash)) {
    // Во входящем payload vcf_phone нет, поэтому разбор vcf_info — рабочий путь.
    // Порядок «поле DTO, затем разбор» переживёт появление vcf_phone во входящем payload.
    $phone = $payload->vcfPhone ?? ContactPhoneExtractor::fromVcf((string) $payload->vcfInfo);
}
```

## Причина

Во **входящем** `ContactAttachmentPayload` поля `vcf_phone` нет: в спеке (`max-openapi/MAX_API_REFERENCE.md`,
`ContactAttachmentPayload`) есть только `vcf_info`, `max_info` и `hash`.
`vcf_phone` объявлено в **исходящем** `ContactAttachmentRequestPayload`, который бот кладёт в своё вложение сам. Поле
`Dto\ContactAttachmentPayload::$vcfPhone` на входе всегда `null`, поэтому потребителям приходилось писать разбор vCard
самостоятельно (в интеграционном проекте — `RequestFlowService::telFromVcf()`).

## Поведение разбора

- Переводы строк: реальные `CRLF`, `CR`, `LF` и их JSON-экранированные литералы `\r\n`, `\n`, `\r` (двойное
  экранирование в транспорте) — как и в `ContactVerifier`, иначе подпись проверилась бы, а номер не извлёкся.
- Свёрнутые строки vCard (строка с ведущим пробелом или табуляцией) разворачиваются до поиска `TEL`, иначе длинный номер
  разрывается. Снимается вся полоса ведущих пробелов (отклонение от RFC 5545 §3.2, где снимается ровно один WSP): для
  номера разницы в реальных vCard нет, лишний пробел в номере хуже. Пробелы внутри значения не трогаются.
- Имя свойства и параметры (`TEL`, `TEL;TYPE=CELL`, `tel;type=work,voice`) регистронезависимы; допускается префикс
  группы (`item1.TEL`, RFC 6350). Кастомные свойства `X-TEL` и `item1.X-TEL` игнорируются — точки перед именем у них
  нет. Значение обрезается от пробелов; пустое значение считается отсутствием, поиск продолжается.
- Нормализации и валидации номера нет намеренно: значение `TEL` может быть любым текстом (`urn:tel:...`, `tel:` URI,
  номер с внутренним расширением), и ядро не должно отбрасывать значения, валидные для бизнеса.
- Ограничение шаблона: двоеточие внутри кавычек в параметре (`TEL;LABEL="a:work":...`) обрывает параметры, в значение
  попадает хвост параметра. Поведение зафиксировано тестом. В реальных payload не встречалось.

## Проверка на реальных данных

Парсер проверен на настоящем payload, а не только на сконструированных входах: единственный подтверждённый захват —
`vcf_info` от Android-клиента, 110 байт, `PRODID:ez-vcard 0.10.3`, `TEL;TYPE=cell:79250000000`, `FN` в UTF-8, `TEL`
раньше `FN`, завершающий CRLF после `END:VCARD`. Разбор отрабатывает и на варианте с литеральными `\r\n`.

Из захвата следуют два факта для потребителя:

- Номер приходит **без `+`**, то есть полный код страны без знака плюс. Ядро значение не нормализует; если номер служит
  ключом (сверка с CRM, дедупликация, привязка лида), единое правило формы нужно применять ко всем точкам ввода, включая
  формы, иначе `+7...` из формы и `7...` из контакта дадут две записи об одном человеке.
- Формат подтверждён для одного номера, и он российский. Аккаунты MAX есть и в других странах, поэтому считать форму
  `vcf_info` универсальной нельзя: код страны может прийти иначе или не прийти вовсе. Универсальная канонизация возможна
  только на выборках из нескольких стран, при необходимости с `giggsey/libphonenumber`; ядро этим не занимается.

Регистрация в MAX возможна только на один номер, поэтому контакт, полученный по кнопке `request_contact`, — это номер
владельца аккаунта, а не произвольное значение: он однозначно идентифицирует пользователя.

## Затронутые сценарии

- Боты с кнопкой `request_contact`: подтверждение контакта и получение номера из одного `vcf_info`.
- `Dto\ContactAttachmentPayload` не менялся: `vcfPhone` остаётся для исходящих сценариев и прямой передачи DTO.
- Замена собственного разбора vCard (в интеграционном проекте i2tech — `RequestFlowService::telFromVcf()`) даёт два
  выигрыша: разворачивание свёрнутых строк (без него длинный номер обрезается на переносе и попадает в базу обрезанным)
  и регистронезависимость имени свойства (`tel:` вместо `TEL`).
