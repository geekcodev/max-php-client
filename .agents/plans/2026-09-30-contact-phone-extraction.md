# План: извлечение телефона из vCard контакта (request_contact)

Статус: **завершён, выпущено в v1.1.8** (2026-09-30, тег `9b3ee06`). Целевая версия была v1.1.7 (MINOR, обратно
совместимо); после снятия релиза v1.1.7 функциональность ушла в состав v1.1.8. Факт: в v1.1.8 вошли `67a21ed`
(функционал) и `175c71f` (документация). Версия v1.1.7 публиковалась на Packagist со ссылкой `ec9ab69`, затем тег
переставили, Packagist заблокировал обновление, после чего версию, GitHub Release и тег удалили. Хронология и проверки —
в release notes.

## Цель

Ядро подтверждает подлинность контакта, но не отдаёт номер телефона. Потребителям приходится писать разбор vCard самим.
Ядро должно отдавать и то, и другое: проверка подписи уже есть, разбора нет.

## Исследование

- Во **входящем** `ContactAttachmentPayload` поля `vcf_phone` нет. `max-openapi/MAX_API_REFERENCE.md:2200-2206` даёт для
  входящего payload только `vcf_info`, `max_info` (объект `User`) и `hash`. `vcf_phone` есть только в **исходящем**
  `ContactAttachmentRequestPayload` (`:2258-2265`), который бот сам кладёт в своё вложение, а не получает от MAX.
- Следствие: `Dto/ContactAttachmentPayload::$vcfPhone` на входе всегда `null`. Поле в DTO есть, но заполняться ему
  нечем, и потребитель, доверившийся ему, получит `null` вместо номера.
- Разбор vCard в интеграционном проекте (i2tech) — `app/app/Services/RequestFlowService.php:1102-1113`
  (`telFromVcf()`), регулярное выражение с `(?:^|\r?\n)TEL(?:;[^:\r\n]*)*[:]`. Это единственный рабочий путь получения
  номера сегодня.
- `src/Security/ContactVerifier.php` закрывает только подпись: HMAC-SHA256 токена над `vcf_info`, восстановление
  реальных CRLF из литеральных `\r\n`, приём хэша в hex и base64 (обычный и URL-safe, с паддингом и без), сравнение
  `hash_equals`. Разбора полей vCard нет.
- `Dto/ContactAttachmentPayload` и остальные DTO — чистые данные: только конструктор, `fromArray()`, `toArray()`.
  Хелперы в DTO не добавляем, это расходится с направлением плана v2.0.0 (типизированная модель).
- Стиль утилит: `src/Internal/Json.php` — `final class` со статическими методами. Новый класс соответствует.
- `docs/api-reference.md`, раздел 9 — таблица расхождений «спека vs реальный API» не содержит случая про отсутствие
  `vcf_phone` во входящем payload. Его нужно внести.
- `README.md:317-318` — раздел про верификацию контакта упоминает только подпись.
- Тест-стиль: `tests/ContactVerifierTest.php` — атрибут `#[Test]`, `PHPUnit\Framework\TestCase`, строки vCard инлайн,
  включая профильный vCard с реальными CRLF и концевым переводом строки.
- `examples/verify-contact.php` показывает только проверку подписи.

## Реализация

1. `src/Security/ContactPhoneExtractor.php` — `final class` со статическим методом
   `fromVcf(string $vcfInfo): ?string`. Без состояния, без HTTP, без исключений, без логирования. Порядок разбора:
    - разделение на строки регулярным выражением, покрывающим все формы переводов строк: реальные `CRLF`, `CR`,
      `LF` и их JSON-экранированные литералы `\r\n`, `\n`, `\r`;
    - разворачивание свёрнутых строк vCard: строка, начинающаяся с пробела или табуляции, присоединяется к предыдущей (в
      vCard перенос значения на следующую строку — норма, иначе длинный номер рвётся);
    - поиск первой строки по шаблону `/^TEL(?:;[^:]*)?:(.*)$/i`: имя свойства регистронезависимо, параметры
      (`;TYPE=CELL`, `;TYPE="work,voice"`) пропускаются, значение берётся по первому двоеточию вне параметров;
    - обрезка пробелов вокруг значения; пустое значение считается отсутствием и поиск продолжается;
    - отсутствие `TEL` или пустой вход — `null`.
2. `Dto/ContactAttachmentPayload` не меняется. Поле `vcfPhone` остаётся для исходящих сценариев и прямой передачи DTO в
   тестах.
3. `docs/api-reference.md`:
    - раздел 7, строка про контакт — добавить, что `vcf_phone` приходит только в исходящем payload, а номер из входящего
      берётся разбором `vcf_info`;
    - раздел 9 — новая строка расхождения: `ContactAttachmentPayload.vcf_phone` объявлен в DTO, но во входящем payload
      отсутствует, извлечение через `ContactPhoneExtractor::fromVcf()`.
4. `README.md`: в разделе про верификацию контакта — извлечение номера и пример кода; в «История изменений» — запись о
   v1.1.7.
5. `examples/verify-contact.php`: после успешной проверки подписи показать
   `ContactPhoneExtractor::fromVcf($vcfInfo)` и вывод номера.
6. `.agents/release/RELEASE_NOTES_v1.1.7.md` по формату «Новое / Изменение (BC) / Затронутые сценарии / Качество».

## Обратная совместимость

- Только добавление публичного метода в новый класс, `ContactVerifier` и DTO не меняются. MINOR, v1.1.7.
- Результат разбора — персональные данные. По A09 номер и `vcf_info` не пишутся в лог: класс не логирует вовсе,
  вызывающий код логирует только факт действия. Это оговаривается в docblock класса.

## Тесты

`tests/ContactPhoneExtractorTest.php` в стиле `ContactVerifierTest` (атрибут `#[Test]`, инлайн-строки, плюс один
обезличенный реальный vCard из фикстуры `tests/Fixtures/vcard/profile-android-real.vcf`):

- `TEL` без параметров и `TEL;TYPE=CELL:+79250557481`;
- регистронезависимость имени свойства и параметров: `tel;type=work,voice:...`;
- vCard с реальными CRLF и завершающим переводом строки (профильный случай, подтверждённый в проде);
- тот же vCard с литеральными `\r\n` после `json_decode` — результат должен совпасть;
- свёрнутая строка: значение `TEL` продолжается на строке с ведущим пробелом;
- несколько свойств `TEL` — берётся первое непустое;
- значение в окружении пробелов — обрезается;
- `TEL` с пустым значением — возвращается `null`;
- vCard без `TEL` — `null`;
- пустая строка и мусор вместо vCard — `null`;
- параметр с двоеточием внутри кавычек (`TEL;LABEL="a:b":+7...`) — задокументированное ограничение шаблона, тест
  фиксирует фактическое поведение, чтобы изменение было осознанным.

Отдельно проверяется, что класс не логирует и не бросает исключений на битых данных.

## Нюансы и риски

- Значение `TEL` может быть любым текстом, а не только телефоном (например, `TEL:urn:...` или номер с внутренним
  расширением). Нормализации и валидации номера здесь намеренно нет: это ответственность потребителя, ядро отдаёт
  фактическое значение из vCard. Иначе ядро начнёт отбрасывать валидные для бизнеса значения.
- Свёрнутые строки: без их разворачивания длинные номера разрываются, поэтому порядок «разделить, затем развернуть,
  затем искать» обязателен.
- Литеральные `\r\n` встречаются из-за двойного экранирования в JSON-транспорте; `ContactVerifier` уже умеет оба
  варианта при хэшировании, разбор должен вести себя так же, иначе проверка пройдёт, а номер не извлечётся.
- Замена параметров регулярного выражения на «жадный `.*`» сломает `TEL;TYPE=CELL` — покрыто тестом.
- Номер не должен попадать в исключения и логи ядра: класс не имеет побочных эффектов.
- Формат номера и канонизация (решение потребителя, 2026-09-30): канон — значение, которое прислал MAX, ядро его не
  трогает. В MAX один аккаунт — один номер, поэтому контакт однозначно идентифицирует пользователя, и если номер служит
  ключом, формы расхождения надо снимать в своём слое. Подтверждён единственный источник истины — один захват `vcf_info`
  от Android-клиента: `TEL;TYPE=cell:79250000000`, то есть полный код страны **без** `+`. Ограничение наблюдения: это
  российский номер, а аккаунты MAX есть и в других странах, поэтому утверждать, что формат `vcf_info` всегда один,
  нельзя. Открытый вопрос: придёт ли для иностранного номера код страны и будет ли `+`
  (для `+79250000000` код страны есть, для номера в национальном записи вида `8...` или `0...` его может не быть — такие
  префиксы различаются по странам). Пока данных нет, любая нормализация в ядре была бы угадыванием, поэтому вердикт:
  `fromVcf()` отдаёт значение как есть, канонизацию потребитель делает у себя, когда появятся реальные выборки по
  нескольким странам. Практическое требование к потребителю уже сейчас: применять одно и то же правило формы ко всем
  точкам входа, включая формы, иначе `+7...` из формы и `7...` из контакта дадут две записи об одном человеке. Если
  понадобится разбор международных номеров, это отдельная задача с библиотекой типа giggsey/libphonenumber, а не
  регулярное выражение в этом клиенте.
