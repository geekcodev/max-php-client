## Подтверждение схемы и перенос из приложения (2026-10-13)

Реальный захват `{ phone, authDate, hash, userId }`, которого не хватало, заменён работающей реализацией: в i2tech класс
`App\Services\WebAppContactVerifier` (временный, в приложении) и `WebAppAuthController` уже проверяют подпись и пускают
пользователя в кабинет; на проде заявки видны. Переносим его в ядро как есть.

Подтверждённая схема (закрепить тестом на вычисленном примере, чтобы правка реализации ловилась регрессией):

```
payload = "authDate=<authDate>\nphone=<цифры>\nuserId=<userId>"   # ключи отсортированы a→p→u, склейка \n
hash    = HMAC-SHA256(payload, bot_token)                        # hash_hmac('sha256', $payload, $token, binary: true)
```

- Секрет и данные: `hash_hmac('sha256', $payload, $token)` — токен ключом, payload данными (порядок аргументов как у
  `ContactVerifier`), без промежуточного `secret_key` из `WebAppData`. Это рабочая схема, перебор кандидатов (таблица в
  разделе «Исследование») не нужен.
- Форма `phone`: сервер подписывает телефон **цифрами без `+` и прочих нецифровых символов**; в приложении стоит
  `preg_replace('/\D+/u', '', $phone)`. Это проверено продакшеном — переносим эту же нормализацию, наугад не расширяем.
- Формат `hash`: приложение принимает hex и base64 (стандартный/URL-safe, с паддингом и без) — как ядровой
  `ContactVerifier`. Оставить обе формы.
- Свежесть `authDate`: replay-guard по `webapp.max_age` (в приложении 86400 c; `0` — выключено). `authDate` — срок
  Unix-секундами.
- PII: payload и телефон не логируются (OWASP A09).

Дополнительно к переносу — общий рефакторинг для устранения дублирования (DRY), см. раздел «План работ».

## Цель

В мини-приложении номер телефона можно получить через мост, но подпись к нему проверяется на сервере, то есть в
PHP-бэкенде. Пакет такого сценария не покрывает: `Security\WebAppDataValidator` умеет только стартовые данные
`initData`, а `Security\ContactVerifier` — только контакт, присланный по кнопке бота `request_contact`. Нужен класс,
который проверяет подпись моста по правилам документации и отдаёт номер только при успешной проверке.

Ожидаемый результат: бот получает номер телефона пользователя из мини-приложения и может использовать его как
альтернативный фактор авторизации, не запрашивая у пользователя контакт в чате.

## Исследование (что уже установлено)

- **Два разных механизма получения телефона, путать их нельзя.**
    1. Кнопка бота `request_contact` (`InlineKeyboardButton` → `ButtonType::RequestContact`). Пользователь жмёт кнопку,
       контакт приходит вложением `contact` в чат: `vcf_info` (vCard) и `hash = HMAC-SHA256(access_token, vcf_info)`.
       Это текущий сценарий пакета: `ContactVerifier` + `ContactPhoneExtractor::fromVcf()` (v1.1.7).
    2. Мост мини-приложения `window.WebApp.requestContact()`. Возвращает объект с номером и подписью, ничего в чат не
       отправляет. Бот по вебхуку не получает ничего; номер уходит на бэкенд мини-приложения.
- **Источники:** <https://dev.max.ru/docs/webapps/bridge> (раздел «Запрос номера телефона») и
  <https://dev.max.ru/docs/webapps/validation> (схема `WebAppData`). Локальная копия справочника Bot API
  (`max-openapi/MAX_API_REFERENCE.md`) раздела о мосте не содержит — только про кнопку `request_contact`.
- **Контракт моста:** `window.WebApp.requestContact()` → `Promise<{ phone: string; authDate: string; hash: string }>`.
  При отказе или сбое — `{ error: { code: string } }`, код вида `client.request_phone.<reason>`, где `reason` —
  `user_refused_provide_phone_number` (отказ) или `request_error` (нет сети / не ответил backend). Точный вид кода
  проверить в логе мини-приложения.
- **Правило проверки по документации:** сравнить присланный `hash` с `HMAC_SHA256(authDate + phone + userId, botToken)`,
  где параметры идут парами `key=value`, склеены через `\n` в алфавитном порядке, а `phone` используется **без `+`**
  (`7**********`, а не `+7**********`). Точный порядок ключей: `authDate`, `phone`, `userId` (a → p → u).
- **Неоднозначность, которую нужно снять экспериментом.** ~~Документ задаёт HMAC только словами и не приводит кода для
  этого случая.~~ **Снято 2026-10-13 (вариант A):** подтверждено рабочей реализацией i2tech — `hash_hmac('sha256',
  $payload, $token)`, см. раздел «Подтверждение схемы и перенос из приложения». Таблица кандидатов ниже оставлена как
  история исследования. Во всей остальной документации MAX запись `HMAC_SHA256(A, B)` означает «A — ключ, B — данные»
  (`HMAC_SHA256('WebAppData', BOT_TOKEN)` — так считается `secret_key`). Отсюда кандидаты:

  | Вариант | secret_key | Подпись (в нотации PHP `hash_hmac('sha256', data, key)`) |
    |---|---|---|
  | A — буквальное прочтение документа | нет | `hash_hmac('sha256', $token, $dataCheckString)` |
  | B — с промежуточным ключом | `hash_hmac('sha256', $token, 'WebAppData', true)` | `hash_hmac('sha256', $secretKey, $dataCheckString)` |
  | C — порядок как в Telegram (токен ключом) | нет | `hash_hmac('sha256', $dataCheckString, $token)` |
  | D — как C, но с промежуточным ключом | `hash_hmac('sha256', 'WebAppData', $token, true)` | `hash_hmac('sha256', $dataCheckString, $secretKey)` |

  Каждый вариант дополнительно проверяется в трёх кодировках подписи: hex в нижнем регистре (основная гипотеза), hex в
  верхнем регистре, base64 (обычный и URL-safe). Итого 12 кандидатов на один захват.
- **Опора на уже работающий код:** `src/Security/WebAppDataValidator.php` реализует схему `initData` и тем самым
  показывает порядок аргументов, который реально использует MAX:
  `secret_key = hash_hmac('sha256', $token, 'WebAppData', true)`, подпись =
  `hash_hmac('sha256', $launchParams, $secretKey)`. Это обратный порядок относительно Telegram и совпадает с их же
  текстовой нотацией, что склоняет к варианту A.
- **Совместимость с текущим `WebAppDataValidator`:** официальный пример `WebAppData` содержит параметры `auth_date`,
  `chat`, `ip`, `query_id`, `user`, `hash`. Валидатор сортирует и подписывает все пары, поэтому новые параметры его не
  ломают; `resolve()` извлекает только `user` и `chat` в `Dto\WebAppIdentity`.
- **Ограничение документации:** данные, полученные через `requestContact()`, можно использовать только для
  взаимодействия с текущим мини-приложением. Это нужно упомянуть в документации пакета.
- **Формат номера перекликается с наблюдаемым продом.** В захвате `vcf_info` от Android-клиента (2026-09-17) значение
  `TEL` приходит **без `+`** — `TEL;TYPE=cell:79250000000`. Документация моста требует убирать `+` при вычислении хеша.
  Если мост отдаст телефон так же, как vCard, `ltrim($phone, '+')` окажется защитной, а не обязательной операцией; это
  уточнится на захвате из пункта «Данные, которые нужны».

## Данные, которые нужны для реализации

> Исторический раздел: данные больше не нужны — схема подтверждена рабочей реализацией (2026-10-13). Оставлен как
> запись о том, как планировалось снимать неоднозначность.

Один захват из работающего мини-приложения. **Токен бота присылать не нужно** и нельзя — перебор кандидатов выполняется
на стороне интегратора, где токен уже есть, а наружу уходит только результат сравнения.

Обязательно:

1. `phone` — значение, которое вернул мост (в исходном виде, включая `+`, если он есть).
2. `authDate` — значение из ответа моста, в исходном виде строкой. Из него сразу видно формат: Unix-секунды,
   миллисекунды или иное — это влияет на проверку свежести.
3. `hash` — значение из ответа моста, в исходном виде.
4. `userId` — `window.WebApp.initDataUnsafe.user.id` для той же сессии.
5. Тот же `botToken`, под которым работает бэкенд (остаётся у интегратора).

Полезно, но не обязательно:

6. Полная строка `WebAppData` (`window.WebApp.initData`) для той же сессии — чтобы проверить, что версия моста и набор
   стартовых параметров соответствуют ожиданиям.
7. Как номер попадает на бэкенд: тело JSON, query-параметр, `start_param` — от этого зависит, что именно принимает
   публичный метод верификатора.
8. Фактический код ошибки при отказе пользователя — чтобы описать его в документации, а не пересказывать таблицу.

Правила обращения с данными: это персональные данные пользователя и его подпись. Захват нельзя коммитить, публиковать и
класть в `tests/Fixtures/`; пароль-менеджёр, репозиторий и чат — не подходят. Достаточно файла вне репозитория
(например, `/tmp/opencode/bridge-sample.json` на этой машине) либо переменной в `.env`, который уже в `.gitignore`.
Номер лучше взять с тестового аккаунта.

## Как получить данные

На стороне мини-приложения (JS, временный фрагмент в консоли или в коде страницы):

```js
const result = await window.WebApp.requestContact();
// успех: { phone: '+7...', authDate: '1771409719', hash: '...' }
// отказ:  { error: { code: 'client.request_phone.<reason>' } }
```

На стороне бэкенда (PHP) — вызвать мост, отправить ответ себе и посчитать все 12 кандидатов подписи, сверив с присланным
`hash`. Значение токена в вывод не попадает, в лог уходят только номер варианта и совпадение:

```php
$dataCheckString = "authDate={$authDate}\nphone=" . ltrim($phone, '+') . "\nuserId={$userId}";
$secretKey = hash_hmac('sha256', $token, 'WebAppData', true);

$candidates = [
    'A:hex' => hash_hmac('sha256', $token, $dataCheckString),
    'B:hex' => hash_hmac('sha256', $secretKey, $dataCheckString),
    'C:hex' => hash_hmac('sha256', $dataCheckString, $token),
    'D:hex' => hash_hmac('sha256', $dataCheckString, $secretKey),
];
// плюс strtoupper и base64/base64url для каждого
```

Совпавший с присланным `hash` вариант и есть искомая схема. Если не совпал ни один — вопрос к поддержке MAX, а не
предположения в коде: подпись проверяет доступ к аккаунту, подбирать её методом перебора нельзя.

## Проектируемый API (схема подтверждена, 2026-10-13)

- `Security\WebAppContactVerifier` — по образцу `ContactVerifier`: `final class`, конструктор `(string $accessToken,
  int $maxAge = 0)`, сравнение только через `hash_equals`, без логов и исключений внутри проверки.
- Публичные методы: `verify(string $authDate, string $phone, string $userId, string $hash): bool` (порядок как в рабочей
  реализации i2tech) и `resolve(...): ?Dto\WebAppContact` — возвращает подтверждённые значения или `null`
  (неверная подпись / просроченный `authDate`).
- `Dto\WebAppContact` — `final readonly` (`?int userId`, `?int authDate`, `?string phone`) с `fromArray()`/`toArray()`,
  по образцу `WebAppIdentity`. Телефон — как пришёл, без канонизации к `+7…` (канонизация — дело потребителя, как в
  `ContactPhoneExtractor`).
- Проверка свежести `authDate` через `maxAge`, как в `WebAppDataValidator`: `time() - authDate <= maxAge`
  (`0` — не проверять).
- **DRY-рефакторинг (в том же релизе).** Сравнение хэша (hex + base64 standard/URL-safe) сейчас дословно продублировано
  в `ContactVerifier` (строки 43–89) и в прикладном верификаторе. Вынести в `Internal\HashMatcher`
  (`final class`, метод `matches(string $expectedBinaryHash, string $hash): bool`; `hash_hmac(..., binary: true)`
  считается вызывающим) и перевести на него `ContactVerifier` и новый `WebAppContactVerifier`. Публичное поведение и
  сигнатуры не меняются — правка внутренняя, регресс `ContactVerifierTest` обязателен.
- Публичный API существующих классов не меняется; добавление классов обратно совместимо (patch v1.1.10).

## Нюансы и риски

- **Привязка к пользователю.** `userId` должен браться из проверенных `initData`, иначе валидная подпись одного номера
  приклеивается к чужому `userId`. Это главный риск реализации, проверяется тестом.
- **Fail-closed.** Без валидной подписи номер не принимается; никаких «мягких» режимов и доверчивого режима.
- **Персональные данные.** Номер и подпись не логируются, не попадают в исключения и в журнал сессий (A02, A09).
- **Нормализация номера.** По документации из хэша убирается только ведущий `+`. Дополнительную нормализацию (пробелы,
  формат) не вводить без требований потребителя; что возвращать наружу — как прислал мост, это решить при реализации.
- **Формат `authDate`** неизвестен до захвата: секунды или миллисекунды. От него зависит проверка свежести.
- **Разграничение сценариев** в документации обязательно: кнопка `request_contact` (контакт в чате, `vcf_info`) и мост
  мини-приложения (`requestContact`) — разные пути с разными подписями. Потребители склонны ждать один универсальный
  способ, поэтому расхождение нужно назвать прямо.
- **Юридическое ограничение** из документации: данные `requestContact()` — только для текущего мини-приложения; это
  упоминается в документации пакета, чтобы потребитель понимал границы применения.
- **Обратная совместимость.** Только добавление классов; существующие сигнатуры не трогаем.
